fmflurry-harness 0.4.26 · fix/guard-false-alarms

Deny the guarded operation, not the ordinary command

A Claude Monolith session logged 44 raw guard_block lines, 34 unique, for coding commands that never push, merge, or write the harness. The same block was stored twice when a global hook and a project hook both ran, and pr-visual-report was saved with an empty guard name.

What changed

1. Parser deny_unparsed only for a guarded op

Read-only git status, diff, log, ls-remote, and merge-base pass inside $() and with a variable -C. Quoted strings are not commands. A quoted heredoc is literal. An unquoted heredoc is data, except $(...) and backticks.

2. Refs 2>&1 is not a branch

git push -u origin feat 2>&1 and the same command piped to tail use feat as the review key. >, >>, and 2>/dev/null are stripped before ref parsing. A redirect onto harness bookkeeping is still a write.

3. KPI One event per block

The user-level Claude or OpenCode hook skips when the repo vendors kpi-emit.sh. A lock drops a second write of the same timestamp, guard, repo, branch, session, variant, and tool. agent-harness kpi report collapses duplicates already in the log.

4. Name pr-visual-report stays

The allowlist is git, ask, secret, budget, and pr-visual-report. kpi feature counts that name instead of dropping it.

Still blocked

  • Push before a recorded code review and security review for that diff.
  • gh pr create --head, and gh pr create with no ## Visual report.
  • ship-init or teardown-merged-worktree chained with &&, ;, or |. One plain command, including a redirect, still passes.
  • A shell write into harness goal bookkeeping, such as echo x > .claude/state/goal.json.
  • git -C $W push, $a push, $(echo git) push, and $'git' push.

Risk
