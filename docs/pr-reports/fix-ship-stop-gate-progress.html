fmflurry-harness 0.4.30 · fix/ship-stop-gate-progress

A stop during tests or review is not “no progress”

ship-stop-gate.sh escalated a healthy autonomous run because, before a PR existed, every stop looked empty. The same hook now runs for Claude, Cursor, OpenCode, Conductor, and Monolith.

What a stop does now

1. Hold
Active goal wait, or a live test, review, or subagent.
▶
Allow
Do not count. stop_blocks and total_blocks stay put.
▶
2. Progress
Worktree tip, .reviews, fix_iterations, or PR head changed.
▶
Reset
stop_blocks = 0
total_blocks + 1
▶
3. Empty
Nothing moved and nothing is running.
▶
Count
stop_blocks + 1
Escalate at 5 consecutive, or 30 total.

How to wait

Explicit agent-harness goal wait "<reason>" --ttl 30m

--ttl is required: 45s, 30m, or 2h, from 1 second through 24 hours. Stops inside the TTL are allowed and not counted. When it expires, the next empty stop counts again.

Detected Background work the host can see

A running background task or subagent in the hook input, a live background_pids entry, a notify inflight marker newer than 15 minutes, or a known test or review command whose cwd is the registered worktree. Cursor forwards status, type, and pids only. OpenCode passes running child sessions.

Risk

An empty stored local_sha is only a baseline, so the first look does not reset the counter. A hold does not update baselines. When the wait expires or the process exits, the next empty stop counts. total_blocks still ends a run that stops 30 times even when each stop showed progress.
